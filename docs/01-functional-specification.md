# NexusBoard — Functional Specification

## 1. Назначение документа

Этот документ описывает **что представляет собой NexusBoard с точки зрения пользователя и продукта**.

Он является основным источником истины по функциональности проекта: какие сущности существуют, какие сценарии должен поддерживать продукт и к какому конечному состоянию мы стремимся.

Технические детали реализации, выбор технологий и внутренняя архитектура вынесены в `02-technical-specification.md`.

---

## 2. Идея проекта

**NexusBoard** — учебная production-like платформа для командной работы.

По смыслу она объединяет идеи из:

- Jira — проекты, задачи, статусы и исполнители;
- Slack — чаты, realtime и упоминания;
- GitLab — activity feed и история действий;
- Telegram — управление активными пользовательскими сессиями по устройствам;
- корпоративных search-систем — единый полнотекстовый поиск по рабочему пространству.

Главная цель проекта — не создать коммерческий аналог этих продуктов, а получить достаточно богатую предметную область для практического изучения TypeScript, Node.js, NestJS, PostgreSQL, MongoDB, gRPC, RabbitMQ, Socket.IO, Redis, search, observability, Kubernetes и распределённых систем.

Развитие продукта ведётся крупными вертикальными функциональными срезами: новая технология появляется внутри реального пользовательского сценария, а не как отдельное упражнение ради технологии.

## 3. Основные сущности

### 3.1. User

Пользователь системы.

Основные данные:

- уникальный идентификатор;
- имя;
- отображаемое имя;
- email;
- дата создания;
- статус учётной записи.

Пользователь может:

- входить в систему;
- иметь несколько активных сессий на разных устройствах;
- состоять в нескольких рабочих пространствах;
- участвовать в проектах;
- создавать и выполнять задачи;
- писать комментарии;
- участвовать в чатах;
- получать уведомления.

При удалении аккаунта пользователь не исчезает из истории системы:

- существующий `userId` сохраняется;
- статус пользователя становится `Disabled`;
- credentials, sessions и персональные данные очищаются;
- вместо пользовательского avatar используется стандартная заглушка удалённого пользователя;
- связи из Tasks, Comments, Chat Messages и других исторических данных продолжают ссылаться на прежний `userId`;
- повторная регистрация создаёт новый User с новым `userId`;
- старый аккаунт не восстанавливается и не связывается автоматически с новым.

### 3.2. Workspace

Рабочее пространство команды или организации.

Workspace содержит:

- уникальный идентификатор;
- уникальное название;
- описание;
- необязательную иконку;
- необязательный цвет/маркер;
- статус `Active | Archived`;
- дату создания;
- дату архивирования, если Workspace архивирован;
- участников;
- проекты;
- каналы общения;
- общую activity-ленту;
- настройки.

Правила:

- пользователь может состоять в нескольких Workspace;
- пользователь, создавший Workspace, автоматически становится его участником и Owner;
- Workspace может существовать без проектов, пока в нём остаётся хотя бы один участник;
- если в Workspace не осталось ни проектов, ни участников, Workspace автоматически переводится в архив;
- архивирование и hard delete — разные операции;
- обычный пользовательский UI не должен использовать hard delete вместо архивирования;
- физическое удаление рассматривается как отдельная административная операция.

Название Workspace должно быть уникальным.

### 3.3. Workspace Member

Отдельная связь пользователя и рабочего пространства.

Workspace membership позволяет:

- иметь доступ к самому Workspace независимо от конкретного Project;
- выдавать доступ к Workspace вручную;
- автоматически давать доступ к Workspace при добавлении пользователя хотя бы в один Project этого Workspace.

Минимально хранятся:

- Workspace;
- User;
- роль;
- дата присоединения.

Текущий набор ролей Workspace:

- Owner;
- Admin;
- Member.

Создатель Workspace автоматически получает membership с ролью Owner.

Если пользователь получает доступ к Project внутри Workspace и ещё не состоит в Workspace, membership создаётся автоматически.

Точный технический способ различать явно выданный Workspace-доступ и доступ, появившийся через Project, не является пользовательским контрактом и может быть уточнён на этапе реализации. Внешнее поведение должно оставаться корректным при переносе Project между Workspace.

### 3.4. Project

Project — набор связанных задач и участников.

Project содержит:

- уникальный идентификатор;
- необязательную ссылку на Workspace;
- название;
- описание;
- статус `Active | Archived`;
- дату создания;
- дату изменения;
- дату архивирования, если Project архивирован;
- участников;
- задачи.

Project может существовать без Workspace.

Для Project действуют роли:

- Owner;
- Member;
- Observer.

Правила ownership:

- у активного Project ровно один Owner;
- пользователь, создавший Project, автоматически становится его участником и Owner;
- второго Owner одновременно быть не может;
- Owner может вручную передать ownership любому Member или Observer;
- при ручной передаче новый участник становится Owner, а предыдущий Owner становится Member;
- при удалении аккаунта Owner ownership автоматически передаётся Member, который дольше всех состоит в Project;
- если Member нет, ownership получает Observer, который дольше всех состоит в Project;
- если других участников нет, Project архивируется без Owner.

Правила Workspace:

- пользователь с достаточным доступом к Workspace может создать в нём Project;
- создатель становится Owner именно Project; его роль в Workspace не повышается автоматически;
- Project можно перемещать между Workspace или делать standalone, устанавливая `workspaceId = null`;
- при переносе Project его участники должны получить доступ к новому Workspace;
- доступ к старому Workspace должен быть пересчитан согласно фактически оставшимся доступам;
- отсутствие проектов само по себе не архивирует Workspace, если в Workspace остаются участники.

Уникальность названия:

- внутри одного Workspace название Project уникально;
- standalone Projects также не должны конфликтовать по имени между собой;
- одинаковое название допустимо для Projects в разных Workspace.

Архивирование Project является бизнес-операцией и финализирует его активные Tasks по правилам Task state machine.

### 3.5. Task

Главная рабочая сущность системы.

Task содержит:

- идентификатор;
- название;
- описание;
- статус;
- приоритет;
- автора;
- исполнителя;
- необязательный Project;
- плановую дату начала;
- плановый срок выполнения;
- фактическую дату завершения при необходимости;
- дату создания;
- дату изменения;
- версию для optimistic concurrency;
- комментарии.

`createdAt` выставляется системой и не редактируется. `updatedAt` обновляется системой автоматически.

Task может быть создана без указания Project. Такая Task имеет `projectId = null` и считается **Unassigned**.

`Unassigned`:

- не является настоящей записью Project;
- является виртуальной коллекцией активных Tasks без Project;
- отображается только если существуют подходящие Unassigned Tasks;
- не может быть переименована, архивирована или удалена как Project;
- Task исчезает из `Unassigned`, когда ей назначается реальный Project.

Статусы Task:

- Todo;
- In Progress;
- Resolved;
- Closed;
- Rejected.

Ручные переходы:

```text
Todo
├── In Progress
├── Resolved
└── Rejected

In Progress
├── Resolved
└── Rejected

Resolved
├── In Progress
└── Closed

Closed   → terminal
Rejected → terminal
```

`Closed` и `Rejected` являются terminal states. После перехода в один из них карточка Task считается замороженной и больше не редактируется.

При архивировании Project:

- `Resolved → Closed`;
- `Todo → Rejected`;
- `In Progress → Rejected`;
- уже `Closed` и `Rejected` не изменяются.

Архивирование и hard delete Task — разные операции. Hard delete должен существовать как отдельная операция и не использоваться обычным frontend-сценарием до появления административного функционала.


### 3.6. Comment

Комментарий к задаче.

Комментарий содержит:

- автора;
- текст;
- дату создания;
- дату изменения;
- упоминания пользователей.

### 3.7. Chat Room

Комната чата.

Возможные типы:

- чат Workspace;
- чат проекта;
- личный чат;
- групповой чат.

### 3.8. Chat Message

Сообщение в чате.

Содержит:

- автора;
- комнату;
- текст;
- дату отправки;
- вложения;
- упоминания;
- дополнительные метаданные.

### 3.9. Notification

Пользовательское уведомление.

Примеры:

- пользователь назначен исполнителем задачи;
- пользователь упомянут в комментарии;
- изменился статус задачи;
- пользователь получил новое сообщение;
- изменился объект, за которым пользователь следит.

Уведомление имеет состояния:

- Created;
- Delivered;
- Read.

### 3.10. User Session

Отдельная авторизованная сессия пользователя на конкретном устройстве.

Примеры:

- Work Laptop — Chrome;
- Home PC — Firefox;
- Phone;
- Tablet.

Пользователь должен иметь возможность управлять сессиями независимо друг от друга.

## 4. Функциональные возможности

### 4.1. Авторизация

Система должна поддерживать:

- регистрацию;
- вход по логину и паролю;
- access token;
- refresh token;
- автоматическое обновление access token;
- несколько одновременных пользовательских сессий.

Пользователь должен иметь возможность:

- выйти из текущей сессии;
- завершить конкретную выбранную сессию;
- завершить все сессии кроме текущей;
- завершить все свои сессии;
- посмотреть список активных сессий.

Для каждой сессии желательно отображать:

- устройство;
- браузер или клиент;
- IP;
- дату создания;
- время последней активности.

### 4.2. Workspace

Пользователь должен иметь возможность:

- создать Workspace и автоматически стать его Owner;
- получить список доступных Workspace;
- открыть Workspace;
- пригласить участника;
- удалить участника;
- изменить роль участника;
- покинуть Workspace;
- архивировать Workspace;
- отличать архивирование от hard delete.

Workspace остаётся активным без Projects, если в нём остаются участники.

Если после операций над участниками и Projects в Workspace не осталось ни одного Project и ни одного участника, Workspace автоматически архивируется.

### 4.3. Projects

Пользователь с достаточными правами должен иметь возможность:

- создать Project внутри Workspace;
- создать standalone Project без Workspace;
- автоматически стать Owner созданного Project;
- изменить Project;
- переместить Project между Workspace;
- отсоединить Project от Workspace;
- архивировать Project;
- отдельно выполнить hard delete через специальную операцию;
- просмотреть Projects Workspace;
- получить подробную информацию о Project;
- добавить участника как Member или Observer;
- передать ownership другому участнику.

При переносе Project между Workspace доступы его участников должны быть пересчитаны.

При удалении Owner ownership автоматически наследуется самым давно состоящим Member, затем самым давно состоящим Observer. Если других участников нет, Project архивируется.

### 4.4. Tasks

Система должна поддерживать:

- создание Task внутри Project;
- создание Task без Project;
- отображение таких Tasks в виртуальной коллекции `Unassigned`;
- назначение/смену Project;
- редактирование Task;
- архивирование Task;
- отдельный hard delete;
- просмотр Task;
- список Tasks;
- фильтрацию;
- сортировку;
- пагинацию;
- назначение исполнителя;
- смену статуса по разрешённой state machine;
- смену приоритета;
- плановую дату начала;
- плановый срок выполнения;
- optimistic concurrency.

Минимальные фильтры:

- по Project;
- Unassigned;
- по статусу;
- по исполнителю;
- по автору;
- по приоритету.

Frontend не должен придумывать собственные правила переходов: backend является source of truth для state transitions, архивирования и заморозки terminal Tasks.


### 4.5. Comments

Пользователь должен иметь возможность:

- добавить комментарий;
- изменить свой комментарий;
- удалить свой комментарий;
- получить комментарии задачи;
- упомянуть другого пользователя.

Упоминание пользователя должно создавать событие для системы уведомлений.

### 4.6. Activity Feed

Система должна хранить значимые действия.

Примеры:

- создан проект;
- создана задача;
- изменён статус задачи;
- назначен исполнитель;
- добавлен комментарий;
- пользователь присоединился к Workspace.

Пользователь должен иметь возможность просмотреть activity feed Workspace или проекта.

### 4.7. Chat

Система должна поддерживать:

- комнаты;
- отправку сообщений;
- получение истории;
- realtime-доставку новых сообщений;
- индикатор набора сообщения;
- online/offline presence;
- упоминания.

### 4.8. Realtime

Без перезагрузки страницы пользователь должен получать:

- новые сообщения;
- новые уведомления;
- изменения открытой задачи;
- некоторые изменения проекта;
- статусы presence;
- typing events.

### 4.9. Notifications

Система должна создавать уведомления на основании событий.

Минимальные типы:

- TaskAssigned;
- TaskCommented;
- UserMentioned;
- TaskStatusChanged;
- ChatMentioned.

Пользователь должен иметь возможность:

- получить список уведомлений;
- отметить уведомление прочитанным;
- отметить все уведомления прочитанными;
- получать новые уведомления realtime.

### 4.10. Search

Система должна предоставлять единый полнотекстовый поиск.

Поиск должен охватывать:

- проекты;
- задачи;
- комментарии;
- сообщения чата.

Результаты должны содержать:

- тип объекта;
- заголовок или краткий текст;
- идентификатор;
- ссылку или данные для открытия объекта.

Должна поддерживаться фильтрация результатов по типу.

### 4.11. Dashboard

Пользователь должен иметь возможность получить составное представление по Workspace.

Пример dashboard:

- информация о Workspace;
- проекты;
- текущие задачи;
- задачи пользователя;
- последние уведомления;
- последние события activity feed.

Dashboard является одним из основных сценариев использования GraphQL.

## 5. Сквозные сценарии

### 5.1. Workspace → Project → Task

Базовый production-like сценарий первой крупной фазы:

1. Пользователь создаёт Workspace и автоматически становится его Owner.
2. Создаёт Project внутри Workspace и автоматически становится Owner Project.
3. Добавляет других участников Project как Member/Observer.
4. Создаёт Task внутри Project либо создаёт Task без Project и видит её в `Unassigned`.
5. Перемещает Task из `Unassigned` в реальный Project.
6. Меняет Task только по допустимой state machine.
7. Архивирует Project и получает автоматическую финализацию его Tasks.
8. При необходимости перемещает Project в другой Workspace; доступы участников пересчитываются.
9. Данные сохраняются в PostgreSQL и переживают restart приложения.

### 5.2. Назначение задачи

Пользователь создаёт задачу и назначает другого пользователя исполнителем.

Ожидаемый функциональный результат:

1. Задача создаётся.
2. Исполнитель сохраняется.
3. Автор получает успешный ответ.
4. Назначенному пользователю создаётся уведомление.
5. Пользователь получает уведомление realtime, если находится online.
6. В activity feed появляется соответствующее событие.
7. Задача становится доступна через полнотекстовый поиск.
8. Dashboard отражает актуальное состояние.

Пользователь не должен знать, сколько внутренних сервисов участвовало в выполнении сценария.

---

## 6. Что не является целью проекта

На первых этапах и в базовой версии проекта не требуется:

- полноценный frontend уровня коммерческого продукта;
- сложная система кастомных workflow;
- billing;
- интеграции со сторонними SaaS;
- полноценный файловый storage;
- аудио- и видеозвонки;
- production-ready multi-region;
- enterprise SSO;
- бесконечная кастомизация ролей.

Такие возможности могут добавляться позднее как отдельные учебные упражнения.

---

## 7. Критерий конечного состояния

Проект считается функционально дошедшим до основной цели, когда пользователь может:

- зарегистрироваться и войти;
- управлять своими устройствами и сессиями;
- работать с Workspace;
- создавать проекты;
- создавать и изменять задачи;
- назначать исполнителей;
- комментировать задачи;
- участвовать в чатах;
- получать realtime-события;
- получать уведомления;
- просматривать activity feed;
- выполнять полнотекстовый поиск;
- получать агрегированный dashboard.

При этом пользовательский функционал должен работать через единый API Gateway, не зависеть от внутреннего разбиения системы и сохранять корректное поведение при временных сбоях отдельных внутренних компонентов.
